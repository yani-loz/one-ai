## Auth hardening (Identity module)

- [ ] **Rotate `JWT_SECRET` — the dev default must never reach prod.** *Why:* the dev default `'dev-only-insecure-secret-change-me-in-prod'` lets anyone forge a valid access token for any org/role; it is the single most dangerous default in the system. **Live-confirmed forged-token blast radius (testing Targets 02/05/07/08):** a forged dev-secret token can read the whole fleet + any org's compliance export/audit trail (TC-PC-025, TC-ER-033), **suspend / legal-hold any org** (one-request availability lockout of any customer — TC-OL-024), and **self-approve break-glass support access** for any tenant (manufacturing customer consent — TC-BG-003). **Exception:** company **erasure** now also requires a sudo-style password re-auth (commit `13da7fe`), so a forged token alone returns **403** there (TC-ER-032) — erase is the *only* forged-token write that's second-factored; every other write + all reads are not. *Where:* `backend/app/core/config.py` (`jwt_secret`, SPEC §6) — supply a strong random secret via env / secret manager in every non-dev environment. The boot guard now **fails closed for any `app_env` outside `{local, test}`** (staging, production, *or a typo'd env*) while the default is unchanged — `Settings.requires_secure_secrets` drives `_forbid_insecure_defaults_outside_dev` (generalized from the prior production-only `app_env == 'production'` check, which let staging / a misspelled env boot on the public dev secret). Residual action here is the operational one: **actually rotate the secret** in every real deployment (the guard only stops the *default* from shipping). **Guard hardened — DONE (testing TC-SG-006):** the guard was an *exact-match denylist* on the two known dev defaults, so a **blank/short `JWT_SECRET`** booted in prod and signed forgeable tokens (`' '` round-trips; literal `''` crashed at issuance). It now also rejects any non-dev JWT secret that is blank, whitespace-only, or under **32 bytes** (RFC 7518 §3.2 HS256 floor) — `config.py` `_forbid_insecure_defaults_outside_dev` + `_MIN_JWT_SECRET_BYTES`, with 5 new `test_config.py` cases and live re-verification (empty / `' '` / 31-byte now RAISE, 32-byte boots). No strength floor on `POSTGRES_PASSWORD` (a blank value can be legitimate IAM/peer/cert auth, and a wrong one fails the DB connection loudly). Residual here is purely operational: actually rotate the real secret per deployment. (Pairs with **Enforce RLS** below — the JWT signature being the *single* isolation layer is what makes a leaked secret catastrophic.)
- [ ] **Move the refresh token to an `httpOnly` + `Secure` + `SameSite` cookie.** *Why:* the lean SPA currently returns the refresh token in JSON and stores it in `localStorage` (deliberate SPEC §8 trade-off) — readable by any injected script, so one XSS = full account takeover via token exfiltration. Reversing this intentional decision is the hardening. *Where:* `backend/app/identity/routes/auth_routes.py` (set/clear cookie instead of returning `refresh_token` in `TokenPairResponse`) + `frontend/src/identity/authClient.ts` / `AuthProvider.tsx` (stop persisting it; rely on the cookie). Keep the access token in memory only.
- [ ] **Add login rate-limiting + account lockout / backoff (throttle IN FRONT of bcrypt).** *Why:* `POST /auth/login` and `POST /platform/login` are unthrottled — open to credential stuffing and brute force, **and** to a **bcrypt CPU-amplification DoS** (testing finding N-01 / TC-PC-073): every login runs bcrypt `rounds=12` *including unknown-email* (via the `DUMMY_PASSWORD_HASH` enumeration defense), so an unauthenticated attacker pins the bcrypt threadpool at zero cost (40 concurrent invalids → ~10.7 s median, all 401, no 5xx). *Where:* a **per-IP throttle / middleware that runs before any bcrypt work** (the CPU cost must be paid by the attacker, not the server) + per-account counters with exponential backoff and temporary lockout, in `backend/app/identity/services/{auth_service,platform_auth_service}.py` and/or middleware. **Do NOT remove `DUMMY_PASSWORD_HASH`** — it defends user enumeration; gate *before* bcrypt, don't skip it. **Partial (2026-06-10 audit fix pass, pending commit):** every bcrypt verify/hash on an async path now runs off the event loop via `asyncio.to_thread` (`verify_password_async` / `hash_password_async` in `security/password.py` — login, platform login, user-create, erasure sudo re-auth), so concurrent logins no longer freeze *other tenants'* in-flight requests (the N-01 latency-amplification half). The threadpool-pinning DoS half remains: the pre-bcrypt throttle is still required — this item stays open.
- [ ] **Size the DB connection pool + uvicorn workers for the target load.** *Why:* `create_async_engine` sets no explicit `pool_size`, so the SQLAlchemy async defaults apply (5 + 10 overflow = **15** connections, `pool_timeout=30s`). It degrades *gracefully* to 200× concurrency today (no knee, no leak — testing finding N-02 / TC-PC-071), but capacity is **accidental, not chosen**, and single-event-loop CPU (bcrypt) is a co-bottleneck. *Where:* `backend/app/core/database.py` (`create_async_engine` pool args) + the uvicorn worker count in the container CMD / deployment — sized deliberately against a measured target, and tracked.
- [ ] **Add MFA (TOTP / WebAuthn).** *Why:* password-only auth is below the bar for an enterprise system holding a whole company's knowledge; platform admin in particular must be MFA-gated. *Where:* identity services + new `schemas`/`routes`; enforce for `platform_admin` first, then `company_admin`.
- [ ] **Add enterprise SSO (SAML / OIDC).** *Why:* mid-market DACH buyers require IdP-backed login (Entra ID / Okta / Keycloak) — it is a sales blocker, not a feature. *Where:* new identity sub-package (e.g. `backend/app/identity/sso/`) issuing the same internal token pair after IdP assertion; per-org IdP config.
- [ ] **Add an access-token denylist for immediate revocation.** *Why:* access tokens are stateless JWTs valid for their full 15-min TTL — today logout, user-deactivation, and **org suspension** cannot kill an already-issued access token. For suspension this means it is **immediate for new sessions but eventual (≤ access-TTL, ~15 min) for in-flight ones** — a suspended org's existing access tokens still reach `/auth/me`, `/users`, etc. (testing TC-OL-005). *Where:* identity `security/tokens.py` + a fast store (Redis) keyed by `jti`; check it in `dependencies.get_current_principal` / `get_current_platform_admin`. Wire `DELETE /users/{id}` (deactivate), logout, **and PC-03a org suspension** to add the relevant `jti`(s).
- [ ] **Replace admin-set passwords with an email-verification + invite flow.** *Why:* `POST /users` and `POST /platform/orgs` currently take a plaintext `password` the admin chooses for the user — the admin learns the user's credential, and there is no proof the email is real. **Impersonation boundary (cross-vendor review, CA-01):** because the admin knows the password, they can sign in *as* that employee — and once the employee plane carries **Tier-1 personal intelligence** (conversations / profiles), that is a direct path past the §7 "admins see knowledge, not conversations" hard boundary. The CA-01 company-admin console (`frontend/src/admin/CreateUserDrawer.tsx`) now exposes this create surface via a UI, so the shortcut is one click for every customer admin — fine for pilot, **must** become a forced first-login reset before the employee/Tier-1 plane ships. *Where:* `backend/app/identity/services/user_service.py` + `platform_auth_service.py` (issue a single-use invite/verify token; user sets their own password on first login) — then drop the `password` field from `UserCreateRequest` / the create drawer.
- [ ] **Add a password policy + breach check.** *Why:* nothing enforces length/complexity or rejects known-breached passwords today. *Where:* `backend/app/identity/security/password.py` (or a validator in `schemas`) — minimum length, complexity, and a Have-I-Been-Pwned k-anonymity range check on set/change.
- [ ] **Revoke the refresh-token reuse family on detected reuse (audit AUD-06).** *Why:* single-use rotation is enforced (a revoked token re-presented → 401), but a detected reuse does not revoke the currently-active descendant chain, so a stolen-then-rotated token's chain survives the victim's later reuse. *Where:* `backend/app/identity/services/token_rotator.py` — on a reuse hit, revoke all unrevoked tokens for `subject_id + subject_type`. **Note:** doing this correctly needs the revoke to **commit** even though the request then returns 401 (the refresh route's session rolls back on the raised error), i.e. an independent transaction — so it pairs naturally with the `audit_log` work (emit a security event). Deferred for that reason; the atomic single-use guarantee itself (AUD-01) is already fixed.

## Platform admin domain (separate auth — never sees tenant content)

- [ ] **Keep platform-admin auth physically separate from company auth.** *Why:* platform admin is Ethera staff with global reach; if its token were accepted on company routes (or vice-versa), one compromised staff login would read every tenant. *Where:* enforced by the JWT `aud` claim — `'platform'` vs `'company'` — checked in `backend/app/identity/dependencies.py` (`get_current_platform_admin` rejects `aud='company'` and `get_current_principal` rejects `aud='platform'`). Verify both directions are 401/403, not silently accepted.
- [ ] **Never let platform admin read tenant content — metadata only.** *Why:* the product promise is data sovereignty; Ethera staff seeing customer conversations/memory is a contract and GDPR breach. *Where:* `backend/app/identity/routes/platform_routes.py` + `services/platform_auth_service.py` — `GET /platform/orgs` returns `OrganizationResponse` (id, name, slug, status, user_count, created_at) and **nothing else**: no content, no costs, no tokens. Audit every future platform endpoint against this rule.
- [~] **Break-glass support access — backend DONE (PR-5 / PC-05, `feat/platform-break-glass`).** A `support_grant` lifecycle (migration `0006`): a platform admin **requests** time-boxed access to one tenant with a reason; a **company_admin must approve** (consent is structural — no platform path can self-approve); approval opens a window; every transition logs to `audit_log` (`support.requested/approved/denied/revoked`, with `expires_at` in the approved event). Access is computed **live** against `expires_at` (no stored `expired`). Content-blindness holds — an active grant unlocks **nothing** today; `support_grant_view.grant_is_active(...)` is the **seam** every future content read MUST gate on, or break-glass is silently bypassed. **Residual:** the two UIs (platform request control + company HITL approval inbox) → PC-05b; pull-only inbox (no notification yet); and wiring the seam once content endpoints exist. *Do not* bolt tenant-read onto the platform-admin role — route it through a current, approved, unexpired grant.
- [x] **Platform `GET /platform/me` + real-identity-on-login (AUD-14) — DONE in PR-2 (`feat/platform-session`).** The frontend no longer synthesises the platform identity from the typed email: `AuthProvider.platformLogin` resolves the real admin via `GET /platform/me` (behind `get_current_platform_admin`), which is now the role source — and on a `/platform/me` failure it tears the half-open session down. `POST /platform/refresh` + `POST /platform/logout` were also added (single-use rotation scoped to `subject_type='platform_admin'`; a company refresh token is rejected), so the session refreshes **in-tab** instead of dying after one access-token lifetime. *Deliberate non-goal:* a hard browser refresh still drops to `/login` — the platform refresh token is held **in memory only** (never localStorage, per the sec-1 hardening), so there is no persisted credential to rehydrate from on mount. That re-login is the intended security posture, not a gap. *Where:* `backend/app/identity/routes/platform_routes.py`, `services/platform_auth_service.py`, `schemas/platform_schemas.py`, `frontend/src/identity/{authClient,AuthProvider}.tsx`.

## Ops & deployment posture

- [ ] **Enforce TLS 1.3 in transit.** *Why:* tokens and tenant data cross the wire in plaintext today — the dev stack is HTTP-only. *Where:* `docker-compose.yml` exposes plain HTTP (`8000`/`5173`); production must terminate TLS 1.3 at the ingress/reverse proxy (and set `Secure` on the refresh cookie above). `security.md`: TLS 1.3 in transit, AES-256 at rest.
- [ ] **Lock CORS — fix the wildcard-with-credentials posture.** *Why:* `allow_origins` is already env-restricted, **but** `allow_methods=["*"]` + `allow_headers=["*"]` with `allow_credentials=True` is far broader than needed; tighten methods/headers to the real surface and pin origins to the actual production frontend domains. *Where:* `backend/app/main.py:34-40` (the `CORSMiddleware` block) + `cors_origins` in `config.py` / env.
- [ ] **Pin the CSP `connect-src` to the real API origin (audit AUD-03 follow-up).** *Why:* `frontend/nginx.conf` now ships security headers including a CSP with `connect-src 'self' https:` — deliberately broad so the SPA can reach an https API at any origin without knowing it at build time. Tighten it to the exact API origin per environment, but **do NOT reduce it to `'self'` alone**: that silently blocks every cross-origin API call, and no test exercises CSP+fetch (the login page makes no request on load), so the breakage would ship undetected. *Where:* `frontend/nginx.conf` (server block + the `/assets/` block, which re-declares the headers).
- [ ] **Introduce API versioning (`/api/v1`).** *Why:* routes are flat top-level today (`/auth/*`, `/users/*`, `/platform/*`, `/health`); shipping without a version prefix makes the first breaking change painful and uncoordinated with clients. *Where:* `backend/app/main.py` router includes + `backend/app/identity/router.py` (mount the aggregated `identity_router` under `/api/v1`); update `frontend/src/identity/authClient.ts` base path. Decide whether `/health` stays unversioned.
- [ ] **Move all secrets to Docker secrets / a secret manager.** *Why:* the stack loads secrets from a flat `.env` (`env_file: .env`) — fine for local, not for prod, where `JWT_SECRET`, DB creds, and IdP secrets need managed, rotatable storage. *Where:* `docker-compose.yml` (`backend` service `env_file: .env`) → swap for Docker secrets / Vault / cloud secret manager in the production compose/orchestration; `config.py` stays the single reader.
