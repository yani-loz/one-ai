# Deep Research Brief — Custom MCP Servers, Claude Cowork as MCP Host, and Cross-Platform Portability

## Your role and mission

You are a senior technical researcher producing an **evidence-grounded capability report** for an engineering team about to build a production remote MCP (Model Context Protocol) server. The report covers six areas:

1. Building **custom MCP servers** under the *current* MCP specification — protocol capabilities, authorization, transports, SDKs, production practice.
2. **Claude Cowork** (Anthropic's agentic product) as an MCP **host** — what it can do, how custom connectors plug in, how enterprises deploy them, its operational limits, and its practical availability.
3. **Exactly what information a remote MCP server can obtain from the host** — per call and per session — and what it structurally cannot see.
4. **Security and the trust boundary** — which host-provided signals a server may rely on, and the threat model for a write-capable server.
5. **The host vendor's data-governance posture** — residency, retention, training, DPA — as it applies to data flowing through a custom connector.
6. **Briefly**: the current state of MCP support in OpenAI ChatGPT and Google Gemini, to assess whether the same server can serve those hosts unchanged.

Work from **live, current documentation — not from your training data**. This field changes monthly; treat anything you "remember" as stale until reconfirmed against a current source.

## Context (why we are asking — read carefully, it shapes every priority)

We are building a "company memory" remote MCP server for enterprise customers: read/search tools over a permission-controlled corporate knowledge base, plus a small set of write tools (record a fact, record a session summary, flag an impact). Hard requirements that shape this research:

- **Server-side per-user permission enforcement.** Every tool call must be attributable to an individual authenticated human. The server maps the auth credential → internal user identity → row-level security in the database. **If the host cannot deliver reliable per-user identity, our security model fails.**
- **The host and the model are UNTRUSTED.** Permission enforcement and write-gating must hold even against a compromised, prompt-injected, or malicious host agent — by construction, not by convention.
- **Multi-tenant SaaS.** One MCP service hosts many customer organizations; org A must never be able to resolve into org B's data.
- **Full audit trail** of every AI access to company data (who, what, when) — legally defensible, not best-effort.
- **Write tools with human oversight** — private-by-default writes, provenance-stamped.
- Customers are **EU-based, GDPR-sensitive, and works-council-scrutinized**; every claim we make must be provable from your sources. A wrong or stale claim in your report becomes an architecture mistake or a false compliance statement.
- Timeline pressure: a working demo against the host is committed for **mid-August 2026** and an EU enterprise pilot for **September 2026**. Practical availability facts matter as much as protocol facts.

There are **two make-or-break axes**, not one: (1) reliable per-user identity under org-wide enterprise deployment, and (2) whether host-mediated usage can be operated in a GDPR/works-council-defensible way given the vendor's data-residency, retention, and DPA terms. Identity can be fully solved and the pilot still dies on axis 2.

Precision beats coverage. An explicitly flagged unknown is valuable; a smoothed-over guess is harmful.

## Step 0 — Product identity confirmation (do this before everything else)

Confirm the canonical **current** product name, official URL, launch/GA date, and last-documentation-update date for "Claude Cowork," and explicitly disambiguate it from adjacent Anthropic offerings (Claude Desktop, Claude Code, claude.ai chat, Projects, Claude for Work/Team/Enterprise) and from any similarly named third-party product. If the product is newly launched or in beta and primary documentation is thin, the correct output is to **report the sparseness and enumerate exactly which capabilities are undocumented** — never to synthesize capabilities from secondary sources. Open the Cowork section of your report with this identity-confirmation block.

## Research questions

### P0 — Identity & authorization 

1. **The current MCP authorization spec.** Which spec revision is current (exact revision date)? Detail the normative auth flow for remote servers: OAuth 2.1 authorization-code + PKCE, dynamic client registration, RFC 8707 resource indicators, RFC 9728 protected-resource metadata, authorization-server discovery. What exactly must a spec-compliant remote MCP server implement **today**?
2. **Token issuer and authorization-server ownership.** When a custom remote MCP server is added to a Claude host, WHO issues the access token the server receives: does the server designate its **own** OAuth authorization server (via RFC 9728 protected-resource metadata / AS discovery), or does the Claude client present a token minted by the host vendor? Specifically: (a) can the server's designated AS **federate to the customer's corporate identity provider** (OIDC/SAML SSO — e.g. Entra ID, Okta, Google Workspace) so the authenticated human is a verified *corporate* identity rather than a host-account identity? (b) what constraints do Claude clients impose on a custom AS — required grant types, PKCE, dynamic client registration vs. pre-registration, redirect-URI rules, token-endpoint client authentication? (c) does any part of the OAuth handshake route through the host vendor's (US) infrastructure, or can the entire identity/auth plane be served from the server operator's own (EU) infrastructure?
3. **How Claude clients actually perform OAuth against custom remote MCP connectors** — Cowork, claude.ai web, Claude Desktop, mobile, Claude Code. Is the resulting token **per-user**? When a Team/Enterprise admin deploys a connector org-wide, does **each user complete an individual OAuth grant**, or is there any shared/service-credential mode?
4. **Identity-claim contents and safe binding to an internal user.** Exactly what identity claims does the token (or its introspection/userinfo response) carry: stable subject identifier, email, name, org/tenant id, verified-email flag? Establish: (a) is there a **stable, immutable subject identifier** that survives email changes and token refresh, suitable as the row-level-security key — vs. binding on mutable email? (b) is the subject an Anthropic account ID, a corporate email, or an IdP subject — and when the customer's Claude workspace uses SSO/SAML, does a *corporate* identity reach the MCP server, stable across sessions and refreshes? (c) what prevents impersonation — can a user set an arbitrary/unverified email on their host account and thereby claim another employee's scope (email-collision / unverified-email takeover)? (d) what is the recommended pattern to bind an external OAuth identity to an internal user record safely at first grant?
5. **Token lifecycle as handled by Claude clients:** refresh behavior, expiry, revocation, what the client does on 401/403 from the server, re-auth UX for the user.
6. **Server-initiated revocation and offboarding, independent of the host.** When an employee is deprovisioned, the server operator must immediately and unilaterally revoke that human's access regardless of host behavior. Establish: (a) can the server invalidate a user's access server-side today — short-lived access tokens, server-side session/introspection, RFC 7009 revocation — and how fast does it take effect? (b) how do Claude clients react when the server returns 401/403 after revocation — silent failure, re-auth prompt, stale retries? (c) is there any directory-sync / SCIM / admin deprovisioning signal from the host, or must revocation be entirely server-driven? (d) does disabling/removing the connector at the host admin invalidate already-issued tokens, or do they live until expiry?
7. **Multi-tenant isolation for one MCP service hosting many customer organizations.** (a) Deployment topology — is a custom connector registered per workspace/org with its own URL (a natural per-tenant endpoint), or is one shared URL expected with the tenant derived from the token? (b) how is the customer org/tenant bound at connector registration and at OAuth time so it cannot be forged by the caller? (c) in streamable HTTP, how is the MCP session id (`Mcp-Session-Id`) bound to the authenticated identity — must the server re-derive user AND tenant from the validated token on **every** call rather than trusting a session id (session-fixation / cross-tenant risk)? (d) known multi-tenant isolation failure modes for remote MCP servers and their mitigations.
8. **Enterprise deployment controls:** Claude for Work / Team / Enterprise admin capabilities for custom connectors — allowlisting, org-wide install, per-user enablement, and **plan gating** (which Claude plans support custom remote connectors at all).
9. **Distribution paths:** adding a custom connector by URL vs. Anthropic's connector directory — process, review/approval requirements, constraints on each path.

### P1 — Claude Cowork as a host: capabilities, wire-level behavior, and practical access 

10. **What Cowork is today** (building on Step 0): platforms, plan requirements, relationship to Claude Desktop and claude.ai chat, its file/workspace model, released feature set. Distinguish shipped vs. announced.
11. **MCP feature support matrix for Claude hosts** (Cowork especially): tools / resources / prompts / sampling / elicitation / roots / notifications; transports (streamable HTTP vs. legacy SSE vs. local stdio); tool annotations (`readOnlyHint`, `destructiveHint`, etc.) and whether the approval UX honors them; structured output / `outputSchema` support.
12. **What the host transmits to the server — exhaustively:** initialize-handshake contents (client info, versions), per-call payloads and metadata fields, progress/cancellation signals. Does **any** conversation content reach the server beyond the tool arguments the model chooses to send? (We must be able to prove to auditors what we can and cannot see.) *Wire-level facts here are empirically-verifiable-only — see evidence rules.*
13. **Human-in-the-loop behavior — and whether the server can force it.** When does the client require user approval of a tool call; per-tool / per-server allow rules; "always allow" persistence. Critically: can the MCP server **guarantee a per-call human confirmation that the client cannot suppress** — opt specific write tools out of "always allow," or force step-up confirmation via elicitation on every invocation — or is approval persistence entirely the user's choice regardless of annotations? This determines whether "every AI write is individually human-approved" is a defensible compliance claim.
14. **Operational limits:** max tools per connector, tool-result size limits, timeouts, concurrency, rate limits, behavior with large results relative to the context window, number of simultaneously active connectors.
15. **Customer-side usage cost of connector traffic at scale.** How do MCP tool-result payloads consume the host plan's token/usage budget — are tool results metered against the customer's Claude plan? Are custom connectors subject to per-user or per-org usage caps, message limits, or throttles that would degrade a multi-user deployment? Is the incremental cost predictable and boundable for a buyer?
16. **Claude's own admin-side visibility — two lenses.** What audit or usage logging does Claude for Work / Enterprise give org admins (audit-log exports, compliance APIs)? And the mirror image, from the employee-surveillance / works-council angle: exactly what **can** an org admin see about an individual employee's conversations and tool usage, can that visibility be disabled, and how does it interact with a non-monitoring commitment? Report both what admin logging *exists* (competitive comparison) and what admin visibility *exposes* (works-council liability).
17. **Org-level memory canary:** does Claude currently offer any form of shared, organization-level memory or cross-user persistent knowledge (memory features, Projects knowledge shared across a team, etc.)? Report its exact current state.
18. **Local capability:** does Cowork support local/stdio MCP servers or packaged desktop extensions, and do those differ in capabilities or approval UX from remote connectors?
19. **Practical access, region, and change management — treat as a go/no-go gate.** (a) What minimum plan, enrollment, or waitlist/beta status is required both to USE Cowork and to install and test a **custom** remote connector against it for development, right now (2026)? (b) Is Cowork available to EU/EEA accounts and EU enterprise workspaces — usable and purchasable in the EU by mid-August 2026? (c) For the lowest tier supporting custom connectors: is purchase self-serve or sales-assisted, minimum seat count, monthly vs. annual commitment? (d) What deprecation/breaking-change policy and notice period apply to the connector interface, and is there a history of breaking changes? (e) What enterprise support/escalation channel, SLA, and public status page exist? If any of this blocks an EU-based developer from building and demoing a custom connector on this timeline, say so plainly as a headline risk.

### P2 — Skills, automation & write-back 

20. **Claude Skills, current state:** format, how they are discovered/installed (individual vs. org-wide distribution), what Anthropic documents about a Skill directing the agent to call specific MCP tools — and **what remains probabilistic** model behavior no documentation can guarantee; how Skills interact with connectors in Cowork specifically.
21. **Unattended / scheduled runs — treat as make-or-break, on par with Q3.** For any scheduled, background, recurring, or agentic-task mechanism in Claude products that can invoke MCP connectors: (a) can an unattended run carry a **specific individual human's** identity/token, or only a shared/service credential? (b) where is the long-lived credential (refresh token) stored — host-vendor (US) infrastructure or elsewhere — how is it refreshed with no human present, and what is the blast radius if leaked? (c) if the human who created the scheduled task is later offboarded, does the task stop, or keep running under a stale credential — and how does the server force it to stop? (d) is the originating human still attributable on each unattended tool call for the audit trail? **State plainly: if unattended runs cannot carry per-user identity, that is a headline finding — the per-user write-provenance model does not extend to scheduled write-back.**
22. **Write-back precedent:** any documented patterns or products where the host agent reports/summarizes back into an MCP connector (memory-style connectors, end-of-session summaries) — what works, what's speculative.

### P3 — Security & the trust boundary 

23. **Trust-boundary classification — a first-class deliverable.** Treat the host and the model as untrusted. Produce an explicit table classifying **every signal the server receives from the host** as either (i) cryptographically/independently **verifiable** by the server (trustworthy) or (ii) **host-asserted / model-controlled** (adversarial input that must never carry a security decision). Cover at minimum: the identity token and its claims, tool-call arguments, the user approval/consent state, elicitation/confirmation responses, tool annotations, the MCP session id, and any "human confirmed" indication. For each host-enforced control (approval UI, annotations, elicitation), state explicitly: *reliable as a security guarantee — yes/no, and why.* This table determines what can be delegated to the host vs. what the server must re-enforce by construction.
24. **Attack classes and mitigations for a write-capable company-memory server.** The read side: confused deputy, token passthrough / audience validation, session hijacking, prompt injection via tool results and via tool descriptions, rug-pull tool redefinition, cross-server shadowing. And the write side, which inverts the risk: **memory poisoning / stored (second-order) prompt injection** — a prompt-injected or malicious host agent persists attacker-controlled content via a write tool that is later retrieved and trusted by *another user's* agent — plus spoofed-provenance writes. Report documented cases and recommended mitigations for agent-writable stores (private-by-default with human-approved promotion, provenance stamping, content quarantine/sanitization, write scoping). Distinguish normative from recommended.
25. **Production remote-server practice:** current state of the official SDKs (Python, TypeScript); streamable-HTTP session management; stateless vs. stateful patterns and horizontal scaling; behavior when tool schemas change (does the client honor `tools/list_changed`?); server versioning practice.
26. **Observability and audit non-repudiation.** What production MCP servers log; protocol affordances for audit (request IDs, session IDs, client identification). Then, for a legally defensible "every AI access" trail: (a) enumerate the exact identity/request metadata capturable per call (verified human identifier stable across refreshes, tenant id, session id, request id, client/version, timestamp, tool, arguments); (b) are there host modes (shared credential, background run) where attribution silently degrades — and can that degradation itself be detected and logged? (c) can the record distinguish "the human explicitly approved this call" from "the model autonomously issued this call under the human's session"? (d) what is structurally unloggable because it never reaches the server?

### P4 — Host-vendor data governance & data flow 

27. **Anthropic's enterprise data-processing posture**, specifically as it applies to data passed to and from a custom remote MCP connector (tool-call arguments AND tool results), for Cowork and the Claude tiers that support custom connectors: (a) **residency** — any EU/in-region processing or storage option, and does it explicitly cover MCP tool traffic? (b) **retention** — how long are prompts, tool arguments, and tool results retained; is a zero-data-retention or no-storage option available, on which plans? (c) **training** — is customer data used for model training by default; how is opt-out established, contractually vs. by setting? (d) **legal** — is a GDPR DPA (Art. 28 terms) offered; current sub-processor list and regions; which attestations does the vendor hold (SOC 2 Type II, ISO 27001, ISO 42001, stated EU AI Act posture)? For each item state whether it applies to **Cowork specifically** or only to the API. Quote exact terms with access dates; anything the docs are silent on is UNVERIFIED — a stale or inferred answer here is actively harmful.
28. **Network topology and data-flow path of one MCP tool call.** When Cowork invokes a remote connector, where does the outbound request physically originate — Anthropic's server-side cloud (which region?) or the user's local desktop? Trace the full path of a tool call and its result: does returned corporate content transit and/or get retained on the vendor's infrastructure, in which region, before and after model processing? State explicitly whether it is structurally possible for tool-result content to never leave EU infrastructure during host-agent usage, or whether host-side inference necessarily processes it. If undocumented, mark UNVERIFIED with the empirical test (stub connector; inspect source IP/region and headers of incoming requests).
29. **Offboarding and right-to-erasure of data residue on the host side.** When a connector is removed org-wide, an employee is deprovisioned, or a deployment ends: what happens to (a) issued OAuth tokens, (b) connector availability, and critically (c) corporate data already surfaced via tool results into Claude conversation history / Projects / memory? Does that content persist in the vendor's retention, and can the customer or user delete it to satisfy a GDPR erasure request? Identify any host-side data that cannot be purged.

### P5 — Brief: OpenAI & Gemini portability (~10% of effort; ≤1 page each)

30. **ChatGPT:** where MCP is supported today (connectors, deep research, developer mode, Agents SDK, Apps SDK), plan availability, auth model (per-user OAuth?), write-tool policies (approval requirements, restrictions on write actions), enterprise admin controls.
31. **Gemini:** where MCP is supported today (Gemini app, Gemini CLI, Vertex AI / ADK, Workspace), auth model, enterprise controls.
32. **Verdict per platform:** can the **same remote MCP server** (per-user OAuth, read + gated write tools) serve this host **unchanged** — **YES / PARTIAL / NO / INSUFFICIENT-EVIDENCE**. If INSUFFICIENT-EVIDENCE, list the specific missing facts rather than forcing a confidence you do not have.
