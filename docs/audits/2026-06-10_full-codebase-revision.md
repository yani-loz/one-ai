# Full-Codebase Revision — One AI MVP

**Date:** 2026-06-10
**Scope:** The entire working tree (backend + frontend + infrastructure + migrations + tests), **not** just the uncommitted Connect/IMAP pile. Eleven review dimensions plus a four-topic cross-cutting gap sweep.
**Method:** Multi-agent adversarial review. Eleven specialist reviewers (one per dimension) read whole files and followed call chains; every **medium-or-higher** finding was then handed to independent skeptical refuters that re-read the source (critical/high got two lenses — *claim-accuracy* and *reachability/impact*) with a refute-by-default stance. A completeness critic then spawned four follow-up reviewers for concerns that fell between dimensions. **73 agents, ~5.8M tokens.** Read-only throughout — no code was run or changed. The two top items were additionally re-read by hand for this report.
**Baseline:** Findings are reconciled against `docs/FIX_BEFORE_PROD.md`; items already tracked there are **not** re-raised as new (a few are flagged where a *new* code path makes an existing deferral unsafe as written).

---

## 1. Verdict

**The codebase is in genuinely strong shape — materially better than its own `FIX_BEFORE_PROD` baseline implies — and the hardest things are verified sound.** There is **no confirmed cross-tenant data leak, no auth bypass, and no silent mail-loss path.** The findings below are **hardening, lifecycle, observability, and data-quality gaps**, plus a cluster of GDPR/compliance plumbing that is missing *and untracked*. None is a confirmed `critical`; the work that remains is real but bounded.

Three things stand out as genuinely well-engineered and were confirmed under adversarial probing:

- **Tenant isolation** — the three-role / two-engine split (`oneai` DDL · `oneai_app` NOBYPASSRLS · `oneai_global` BYPASSRLS) makes the privilege boundary a *static pool property*, so a mis-wire is a one-file, review-visible mistake. All 14 tenant tables carry `org_id NOT NULL` + `ENABLE/FORCE` RLS created in the same migration as the table; a dynamic standing-invariant test enumerates them and live-proves two-role row filtering. Every `session.execute` in `app/` was swept — no unscoped tenant query exists.
- **Auth / identity** — audience-pinned dual domains verified inside `jwt.decode`, single-use refresh rotation via atomic conditional UPDATE, bcrypt + dummy-hash enumeration defense, structurally-impossible-to-self-approve break-glass, lock-ordered erasure. The strongest layer in the system.
- **Never-lose-mail core** — the claim/fence protocol and the `highest_contiguous_uid` cursor invariant hold under every interleaving the reviewers could construct (UIDVALIDITY reset, dropped FETCH, failed parse, dedup collision, stolen claim). The *math* is correct; the issues are in the liveness/visibility ring around it.

And the project's discipline is real: `FIX_BEFORE_PROD.md` is an exemplary, evidence-linked deferral register; backend code-quality is near-spotless against the repo's own rules (135/138 files under 300 lines, zero `raise Exception`, no dead code, no TODOs, near-total typing, flawless layering); test discipline is strong (no `unittest.mock`, real ASGI + real RLS Postgres, cross-tenant negatives on the request-path surface).

**The honest one-line summary:** the code that exists is production-grade in its discipline; what's missing is (a) a handful of *liveness and observability* defenses around the new background sync engine, (b) the *GDPR/compliance plumbing* for the connector plane (audit trail, data-subject rights, credential-update, lifecycle-reaches-sync), and (c) the *production deployment path itself*, which today exists only as Dockerfile targets.

## 2. How to read this

Findings are grouped **net-new** (the value of this pass — not in `FIX_BEFORE_PROD`) vs **escalations** (an existing deferral made unsafe by new code) vs **already-tracked** (verified, listed briefly). Within net-new they're ordered by adversarially-adjusted severity. Every entry cites `file:line` that a reviewer (and, for the top items, I) read directly.

Severity calibration used here: **critical** = exploitable cross-tenant leak / data loss / auth bypass · **high** = serious defect likely to bite the first production tenant · **medium** = real defect, bounded blast radius · **low/info** = hygiene / future-proofing.

## 3. Net-new findings — HIGH

### H-1 · IMAP connection-**test** path disables TLS certificate verification
`backend/app/connectors/imap/client.py:68-72` · *secrets-input-hardening* · **confirmed (re-read by hand)**
`DefaultImapClient._blocking_verify` builds `imaplib.IMAP4_SSL(host, port, timeout=…)` with **no `ssl_context`** → stdlib falls back to `ssl._create_stdlib_context()` (`CERT_NONE`, `check_hostname=False`). The **fetch** path (`fetch_session.py`) correctly uses `ssl.create_default_context()`. So a network MITM on the *test* path can present any cert and capture the plaintext mailbox credential at LOGIN. **Fix:** pass `ssl_context=ssl.create_default_context()` (share one helper with the fetch path; assert `CERT_REQUIRED` in a test). One line; do before any real mailbox is tested over an untrusted network.

### H-2 · First sync of a large mailbox can never complete (unbounded FETCH command line)
`backend/app/connectors/imap/sync/imap_fetcher.py:74` → `fetch_session.py:187,200` · *ingestion-sync* · **confirmed ×2 (re-read by hand)**
`fetch_incremental` passes the **entire** folder's new-UID list to `fetch_sizes` *before* `batch_by_bytes` runs; `_blocking_sizes`/`_blocking_fetch` join every UID into one `UID FETCH …` command. On a real corporate first sync (tens of thousands of UIDs) the command line exceeds common server caps (e.g. Dovecot `imap_max_line_length` 64 KB ≈ ~9k UIDs); imaplib **raises** on the BAD reply, the run finalizes `error`, and **every retry fails identically** — the mailbox can never finish its first sync. The team raised the *response* line cap (`imaplib._MAXLINE`, `fetch_session.py:38`) but never the *command* side; the spike only validated ~1.5k messages. **Fix:** chunk the sizes/fetch by UID count (≤~500–1000) or compress contiguous runs to `min:max` ranges; add a 50k-UID test asserting per-command bounds.

### H-3 · CPU-bound parse runs synchronously on the shared event loop, with no message-size cap
`backend/app/connectors/imap/services/email_ingest_service.py:79,177` · *ingestion-parse-store* · **confirmed ×3**
`parse_email` (full MIME tree build + a second header parse + sha256 + `html2text` flatten of arbitrarily large HTML) and `extract_text` run **inline on the FastAPI event loop**, because the runner is an in-process asyncio task and compose runs a single uvicorn worker — one loop for all tenants. There is no max `RFC822.SIZE`: `batch_by_bytes` gives an oversize message its own batch but never refuses it. Consequences: (a) API latency spikes for **all** tenants during any sync; (b) a single parse longer than `STALE_SECONDS=300` starves the heartbeat on the same loop → the claim can be stolen → a duplicate run starts; (c) unbounded memory on a pathological message. **Fix:** offload the (documented-pure, DB-free) `parse_email`+`extract_text` pair via `asyncio.to_thread`, and add a configurable size cap above which a message is stored as a degraded `parse_status='failed'` stub (existence preserved, cursor advances).

### H-4 · A deterministic non-`RecursionError` parse failure stalls a folder forever; the promised "dead-letter" does not exist
`backend/app/connectors/sync/connector_sync_runner.py:284-332` + `imap/parsing/email_parser.py:95-109` · *parse-store* (also surfaced by *sync* & *code-quality*) · **confirmed → qualified (high/medium)**
`parse_email` degrades **only** `RecursionError` to a stored stub; any *other* deterministic exception (e.g. `html2text` on pathological markup — attacker-sendable by anyone who can email the mailbox) propagates, is tallied `failed`, and is **never accounted**, so the cursor stops at that UID permanently. The runner comment at `:318-319` promises dead-lettering "after a second failure" — **no such mechanism exists.** *Important nuance:* the never-lose-mail invariant **holds** — the mail is not lost, the folder **stalls loudly** and re-fetches. The real harms are (a) an attacker-triggerable permanent folder freeze, (b) every subsequent sync re-fetches+re-parses the whole folder tail (cost grows without bound), and (c) the docstring asserts behavior the code doesn't implement. **Fix:** implement what the comment claims (on a UID already in carried-forward `failed_uids`, store the degraded stub and account it), **or** extend the degraded path to all deterministic parser-internal exceptions; delete the false comment either way.

### H-5 · Unbounded concurrent syncs exhaust the one 15-connection tenant pool → cross-org availability DoS
`backend/app/connectors/sync/sync_task_registry.py:32-40`, `core/database.py:38-48`, `connector_sync_runner.py:177-210` · *gap:sync-pool-exhaustion* · **confirmed**
All three engines are built with no pool args → SQLAlchemy async default **5 + 10 = 15** connections, `pool_timeout=30s`. `tenant_engine` is a process-wide singleton serving **both** every org's HTTP traffic **and** every background runner. Nothing caps concurrent syncs (`_RUNNING_SYNC_TASKS` is a bare set; `claim_for_sync` is per-*connection* only; no per-org connection cap). Amplifier: `_sync` autobegins a transaction at `get_in_org` (`:177`) that stays **idle-in-transaction through the entire `count_pending` IMAP scan** (`:206`, minutes on a first sync) before committing at `:210`. So ~pool-size concurrent initial syncs pin the whole pool; then **every tenant request across every org** blocks 30s and errors. Reachable by one `company_admin` creating N mailboxes and triggering sync on each — **or** a normal customer with 8–10 mailboxes clicking "sync all" after onboarding. *(Verifier corrected the seed: steady pin is ~1 conn per in-flight initial sync, not 2 — conclusion stands.)* This **escalates the N-02 pool-sizing deferral, which was measured against millisecond HTTP holds and is unsafe as written for the new long-lived workload.** **Fix:** process-wide sync-concurrency semaphore (well under pool_size); release the DB session during `count_pending`; a separate small pool for background syncs; a per-org connection cap.

### H-6 · No credential-update path: recovery from a rotated mailbox password is DELETE, which CASCADE-destroys the whole ingested corpus
`backend/app/connectors/routes/connector_routes.py:35-136` (+ models `email.py:62`, `connector_sync_run.py:41`) · *gap:credential-rotation-cascade-loss* · **confirmed**
Providers rotate/revoke IMAP app passwords routinely (often forced). The connector surface is exactly create/list/get/test/disable/enable/sync/delete — **no credential update**, and the `(org_id, connector_type, username)` duplicate guard returns 409, so an admin **cannot** stand up a verified replacement first: delete-first is structurally forced (the frontend docstring `AddMailboxDrawer.tsx:11` canonizes "delete + re-add"). DELETE cascades away **every** `email_message`, recipient, attachment, the per-folder cursors, **and the entire sync-run ledger** in one statement; re-create gets a new id + zero cursor. Any message expunged from the server since first ingest (plus all attachment `extracted_text`, whose bytes were discarded by design) is **permanently lost.** The bitter irony: a runner built around never losing one email, whose only recovery from the *most common* operational event silently loses the whole mailbox. **Fix:** `PATCH /connectors/{id}/credential` — verify-then-swap (persist the new ciphertext only after a successful `verify_connection`), audit-logged, write-only; plus a non-destructive "Disconnect (keep data)" terminal state (already in the design doc §8). Track as a new gate (suggest CA-CONN-06).

### H-7 · The connector lifecycle writes **zero** `audit_log` rows — the highest-blast-radius admin surface is the only unaudited one
`backend/app/connectors/routes/connector_routes.py:35-136` · *gap:connector-audit-coverage* · **confirmed**
None of the nine connector endpoints (create-with-credential, test, disable, enable, sync trigger/status, delete) emits any audit event; there is no `connector.*` or `sync.*` `AuditAction` namespace. So "who connected this mailbox / who triggered this sync / **who deleted the corpus**" is unanswerable from any table — and (with H-6) DELETE erases the corpus **and** the only record it ever existed, atomically and untraceably, invisible to the GDPR compliance export. Worse, actor identity is **structurally discarded** at the route boundary (services take only `org_id`; `ConnectorSyncRun` has no `triggered_by`). For a GDPR product, connecting an employee mailbox is the initiation of Art. 30 large-scale processing. **Fix:** add a `connector.*` namespace (created/deleted with cascaded-row counts/disabled/enabled/verify_failed, `sync.started` with actor) emitted from the service layer on the tenant session (`audit_log` is deliberately RLS-exempt for exactly this); plumb the actor now while there's one connector type. Mechanically trivial (no import cycle — connectors already imports identity). Add a `FIX_BEFORE_PROD` row.

### H-8 · GDPR org-erasure has **no cross-tenant blast-radius test**
`backend/tests/identity/routes/test_erasure_routes.py` · *testing-adequacy* · **confirmed ×2**
Erasure is the most destructive multi-table write in the system (`delete_all_in_org` + `delete_for_org_users` + `scrub_decider_emails`). **Every** erasure test seeds exactly one org, so a regression that dropped an `org_id` filter in any of those three methods would **mass-delete every tenant's data and the suite would stay green** — a direct violation of `testing.md`'s non-negotiable. **Fix:** one test — seed org A and B (each with admin + login-created refresh token + decided support grant), erase A, assert B's users/tokens/decider-email survive and B's admin can still log in.

### H-9 · No data-subject-rights path (Art. 15/16/17) for harvested correspondents — and it's untracked
`docs/FIX_BEFORE_PROD.md:82-85` (gap), schema `imap/models/email.py:72-94,117-123` · *gap:data-subject-rights* · **confirmed**
A third-party correspondent whose PII the connector harvested (without any interaction of theirs) has **no** code path for access/rectification/erasure, and the production-gate file doesn't track it. `FIX_BEFORE_PROD:82(a)` is per-*employee* erasure (the `users` table — a correspondent has no row); `82(b)`/CA-CONN-01/03 are *org-level* offboarding (useless for one subject against a live tenant). The schema makes the naive fix actively wrong: person PII is **denormalized** into `email_message.from_name/from_address`, `email_recipient.name/address` ("raw, as-seen"), and the verbatim header JSONB, while person FKs are `SET NULL` — so deleting a `person` row scrubs **nothing** and destroys the join key needed to find the leftovers. There's also no lookup-by-address read surface (only the *normalized* `person_email` key is queryable; raw columns are unindexed) and role/automated addresses have no person row at all. For a product selling GDPR-foundationality to DACH DPOs, Art. 28(3)(e) makes this a mandatory DPA clause asked in every procurement; a single DSAR starts a one-month statutory clock the system can't meet. **Fix (no code now, a *gate* now):** a `FIX_BEFORE_PROD` item with CA-CONN rigor — find-by-address query spec (person + person_email + person_alias + denormalized email columns + headers, normalized + raw-variant match), a per-column scrub-vs-retain map with the **scrub-before-delete ordering invariant**, a written body-text retention position (Art. 17(3) correspondence basis), and the Art. 15 export shape. Promote the one-line CA-03 roadmap mention into a scoped epic.

## 4. Net-new findings — MEDIUM

### Tenant isolation / privilege
- **M-1 · 0009 grants the RLS-enforced tenant role full DML on the 5 non-RLS platform tables** — `0009_enforce_rls.py:86-98`. `oneai_app` (NOBYPASSRLS) gets blanket `SELECT/INSERT/UPDATE/DELETE ON ALL TABLES`, so `platform_admins` (staff bcrypt hashes), `refresh_tokens`, `audit_log` (cross-org PII), `organizations`, `alembic_version` are protected on the tenant plane by app-layer discipline alone — the single-layer posture 0009 was built to retire. A SQLi/ORM bug in any tenant request reads them with zero DB backstop. **Fix:** follow-up migration — narrow `oneai_app` to DML on the 14 tenant tables + INSERT-only on `audit_log`, REVOKE the rest; lock with a grant-matrix invariant test. *(Confirmed; also surfaced by auth & infra dims.)*
- **M-2 · Org lifecycle never reaches the sync plane** — `erasure_service.py:115-118`, `platform_org_service.py`. Neither suspension nor erasure stops an in-flight `ConnectorSyncRunner` (it checks only `is_disabled` + the run fence, never org status) nor sets `disabled_at` on connections, so fresh email PII keeps landing in a **suspended or even erased** org, and a ≤15-min stale token can start a *new* sync post-erasure — falsifying the deletion certificate. Escalates CA-CONN-01 + the access-token-denylist deferral (both predate a live ingestion engine). **Fix (cheap):** have suspend + erase set `disabled_at` on all the org's connections (the runner already aborts on disabled at the next batch).

### Sync liveness & observability (the ring around the correct cursor)
- **M-3 · Heartbeat loop dies permanently on the first transient DB error** — `connector_sync_runner.py:334-348`. The whole `while True` is under one try/except; a single pool-checkout timeout or transient disconnect exits the loop for the rest of the run. Liveness then rides solely on per-batch writes, and a batch over `STALE_SECONDS=300` makes a **healthy** run stealable. **Fix:** catch per-iteration, log, sleep, re-open the session; exit only on cancel or fenced-False.
- **M-4 · A wedged IMAP op holds the claim forever** — `fetch_session.py:123-125` + runner heartbeat. No `asyncio.wait_for` anywhere in the IMAP path; the heartbeat attests *process* liveness, not progress. An unbounded `getaddrinfo` (the documented CA-CONN-02 DNS gap) or a trickling server that resets the 60s socket timeout per recv keeps the claim fresh forever — `POST /sync` 409s until an app restart, and the wedged non-daemon executor thread can even block process shutdown. **Fix:** per-operation deadline (`wait_for` + force-close socket on timeout), or a progress-watchdog that lets stale-reclaim recover a wedged run.
- **M-5 · Folder-level failures are completely silent** — `imap_fetcher.py:52-56,67-70`. A LIST failure → `[]` → whole sync "succeeds" with 0 messages; a SELECT failure / missing UIDVALIDITY → `continue` with no log/counter/ledger signal. A folder that persistently fails SELECT (ACL change, `\NonExistent`, a quoting edge) is **silently excluded forever** while every run reports `succeeded` and `last_sync_error` stays NULL — contradicting the loud-failure ethos. **Fix:** log + count skipped folders; thread a skipped count to the ledger; treat a LIST failure as a run-level error.
- **M-6 · The poison stall is invisible to every API consumer, and a clean finalize wipes the error signal** — `connector_sync_runner.py:238-248,357-388`. `_sync` always finalizes `ok=True` even when `counts.failed>0`, so `last_sync_error` is NULLed and the connection reads as a clean idle sync. The only durable failure signals (`messages_failed`, `failed_uids`) are exposed by **no route** (`SyncStatusResponse` carries neither; the run-history repo method is dead code), and `parse_status='failed'` stubs have **no index, no query path, no consumer** — so the documented "queryable flagged row" / "delete the row and re-sync" recovery is currently impossible (and wrong for RecursionError stubs, whose cursor already advanced). Meanwhile each run re-downloads the folder tail above a stalled cursor, growing forever. **Fix:** write a non-fatal summary into `last_sync_error` when `failed>0`; expose `failed_count` + run history; add a partial index on `parse_status='failed'` + an ops query/route; document the real reprocess procedure (delete stub **and** reset the folder cursor).
- **M-7 · Three load-bearing docstrings describe a step-over / dead-letter mechanism that does not exist** — `connector_sync_cursor.py:12-13`, `0011_sync_runner_state.py:10`, `parsing/models.py:11-15` (+ the runner comment in H-4). The model/migration say `failed_uids` are UIDs the advance "steps over"; the code does the **opposite** (stall by design). `parsing/models.py` still asserts the *old* raw-byte dedup invariant ("ALWAYS sha256 of RAW bytes — never the Message-ID"), the exact opposite of the current DQ-B05 content-identity key. Under this repo's A4 "docs are runtime input" rule, a future editor "fixing" the code to match these would reintroduce silent mail loss / the 40% folder-duplication. **Fix:** rewrite all four to the implemented semantics. *(This is documentation, but flagged at medium precisely because the repo treats docstrings as contract.)*

### Entity-resolution data quality (all confirmed)
- **M-8 · Person-hood gate misses compound automation local-parts** — `flags.py:25-40,111-116`. Exact-frozenset match only; `messaging-digest-noreply@`, `github-noreply@`, `alerts@`, `updates@` (which set `List-Unsubscribe`, not `Auto-Submitted`) still mint Persons. The audit's 38-machine-persons class is only partially closed. **Fix:** affix rule for the `noreply`/`donotreply`/`bounce-` family.
- **M-9 · DMARC-munged mailing-list mail mints one pseudo-Person per list and drops the real human** — `flags.py:95-108` + `email_ingest_service.py:139-151`. Under p=reject From-munging (Google Groups/Mailman — the corporate norm), From = the list address and the human survives only in Reply-To, which is categorically suppressed. The list becomes a Person accreting every poster's name as aliases. **Fix:** detect `List-Id`+From=list (or "via" display) → suppress person-hood; park the Reply-To human.
- **M-10 · `display_name` backfill is first-non-empty-wins → garbage wins permanently** — `person_repository.py:75-91`. A bare address, RFC2047 mojibake, or a spoofed From display phrase (inbound mail is unauthenticated) names the person forever; the real name one email later can never displace it. The audit specified "best non-empty name." **Fix:** quality-gate the candidate (reject `@`/address-equal/mostly-non-letter) and allow an address-as-name to be replaced.
- **M-11 · `is_internal` is first-writer-wins and never reconciled** — `entity_resolver.py:118-146`. Computed from whichever connection synced the person first; in a multi-mailbox org the CEO's gmail ingesting `colleague@acme.com` before the acme connection marks that colleague external forever. The model docstring claims it's "set later by the resolver" — it isn't. **Fix:** promote `False→True` on a later sighting from a matching own-domain connection; long-term derive at read time from the tenant's own domains.
- **M-12 · B03 (eTLD+1 company fragmentation) is neither fixed nor tracked** — `entity_resolver.py:166-199`. The company key is the full host, so one org splits into N companies (audit: `atlassian.net`→4); the D01 observe-always rule now mints companies for every non-generic domain, and mailer subdomains are the most fragmentation-prone. **It is the only data-quality audit candidate with no code fix and no `FIX_BEFORE_PROD` row** — violating the file's own convention. **Fix:** record the deferral now; real fix is PSL-based registrable-domain reduction (not last-2-labels, which over-merges `.co.uk`).
- **M-13 · Generic-domain list misses ccTLD/subdomain variants → over-merges strangers into a fake company** — `address_rules.py:45-78`. Exact-match frozenset misses `outlook.fr/.it/.es`, `hotmail.ch`, and **all** subdomains of listed providers; each miss links every unrelated contact on that provider into ONE Company via `person_company` — the one over-merge/corruption class the module's philosophy promises to avoid (D01 now mints it unconditionally). **Fix:** suffix match on the registrable domain + extend the EU provider/ccTLD families.
- **M-14 · `connector.username` is not validated as an email but the resolver assumes it is** — `connector_schemas.py:35` + `entity_resolver.py:61-62`. Many on-prem IMAP deployments (Exchange `DOMAIN\user`, bare usernames — common in DACH mid-market) log in without an address; then `extract_domain`→None, so `_is_internal` never matches and **every** person/company is marked external and **every** email "inbound" — whole-tenant misclassification, silent, feeding the future Learn layer. **Fix:** validate `username` as addr-spec for IMAP, or add a validated `mailbox_address` field defaulting to `username` when it contains `@`; warn at create/sync when neither yields an address.

### Frontend

Every visitor's IP goes to Google US on page load; remote-loading Google Fonts is a litigated GDPR violation in Germany (LG München I, 3 O 17493/20) — for a product *selling* DACH data-sovereignty. ### API contracts / infrastructure
- **M-17 · OpenAPI `/docs` + `/openapi.json` served unauthenticated in all environments** — `main.py:55-58`. Publishes the full platform-admin API map for recon in prod. Not tracked. **Fix:** `docs_url=None/redoc_url=None/openapi_url=None` when `requires_secure_secrets`; add a `FIX_BEFORE_PROD` row. *(Surfaced by both api-contracts and infra.)*
- **M-18 · List endpoints return unbounded collections** — `user_routes.py:34-40` (+ orgs/connections/support lists). No limit/offset → DoS-by-growth; inconsistent with the audit reads that already cap at 200. *(Verifier adjusted to low — bounded today by small data — but it's a real omission.)* **Fix:** bounded `limit`/`offset` with a hard ceiling.
- **M-19 · Prod backend image cannot fulfill its own boot contract** — `backend/.dockerignore:15`, `Dockerfile:46`. `.dockerignore` excludes all of `scripts/`, so `provision_roles` (mandatory after every migrate, to give the runtime roles LOGIN) is **absent from the shipped image**, and **no prod compose/entrypoint exists** (FIX_BEFORE_PROD references one that isn't there). A first deploy fails DB auth. CI never `docker build`s either target, so this ships undetected. **Fix:** ship `provision_roles.py` (keep the seed out), add a documented prod entrypoint/migration job, add a CI image-build+smoke job. *(The production deployment path is the one genuinely unbuilt piece — treat it as a feature to design.)*
- **M-20 · Dev compose publishes Postgres on `0.0.0.0` with a default superuser password while the volume holds real mailbox PII** — `docker-compose.yml:10-14`. `POSTGRES_PASSWORD:-oneai` + `5432:5432` (netstat-confirmed listening); the dev DB now contains a real ingested corpus. Anyone LAN-adjacent to the dev laptop can read it as superuser (8000/5173 exposed the same way). *Scoped to the developer's machine, not prod code, but a real exposure.* **Fix:** bind published ports to `127.0.0.1`; drop the `:-oneai` fallback so compose fails loudly without `.env`.
- **M-21 · Container attachment parts dump raw base64 source into `extracted_text`** — `email_parser.py:272-300`. `message/rfc822` forwards and nested multiparts are serialized whole (`part.as_bytes()`), and because `message/rfc822` is on the text allowlist, a forwarded email's entire MIME source — RFC2047 headers, quoted-printable bodies, megabytes of base64 — lands in `email_attachment.extracted_text`, bloating the table and poisoning the future Ask/embedding layer; nested multiparts lose their inner attachments entirely. **Fix:** recurse into `message/rfc822` (subject + flattened body + enumerate its attachments) or drop it from the text allowlist until recursion lands.

### Testing
- **M-22 · Sync persistence layer lacks cross-tenant negatives** — `test_sync_persistence.py`. Only `claim_for_sync` has one; cursor repo, run repo, the four fenced writes (tested for run-id fencing but **not org fencing** — dropping `org_id` from `_fenced_update` would pass the suite), and `is_disabled` have none. Bounded exploitability (connection_id is an org-bound UUID) but a `testing.md` non-negotiable. **Fix:** a small cross-tenant matrix.
