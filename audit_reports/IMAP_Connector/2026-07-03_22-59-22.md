## Findings

### 🟠 High

#### H1. Single-part (non-`multipart`) document emails are silently dropped — no body, no attachment, no extraction

- **Root cause:** `email_parser.py:_extract_attachments` (line 284) collects attachments via
  `message.iter_attachments()`, and `_extract_body_text` (line 254) reads the body via
  `message.get_body(preferencelist=("plain","html"))`. When an email is **not** a multipart and its
  top-level `Content-Type` is a document type (e.g. `application/pdf`, `application/octet-stream`,
  a bare `image/*`), BOTH return nothing: `get_body` has no text candidate → returns `None` → body is
  `''`; `iter_attachments()` iterates only the *sub-parts of a multipart* → yields nothing for a
  single-part message. The document payload — which is the entire message content — is never captured
  as body text, never stored as an `email_attachment` row, and never extracted. The email persists as
  an empty shell (`body_text=''`, `has_attachments=false`, `word_count=0`).
- **Evidence:** 4 Kaufland order emails, subject `Кауфланд Пор. № … -Инф. в приложението`
  ("info in the attachment"), are stored empty. Reproduced with the exact parser primitives on
  `INBOX.Workshops.Kaufland/.../6.eml`, `12.eml`, `28.eml`, `36.eml`:
  `top content-type = application/pdf`, `get_body(...) = None`, `iter_attachments() count = 0`,
  leaf parts = `[('application/pdf','attachment')]`. In the DB these 4 rows have `body_text` empty,
  `has_attachments=false`, and **0** `email_attachment` rows — the order PDF is gone. (Contrast the
  reply `9.eml` in the same thread, a proper `multipart/related`: 2,036-char body + 11 image
  attachments, stored correctly.) The corpus-wide `has_attachments` flag is otherwise perfectly
  coherent (0 mismatches either direction), so this is specifically the single-part-document blind spot,
  not a flag bug.
- **Impact:** Any company that installs the IMAP connector loses every email that arrives as a bare
  document with no MIME wrapper — extremely common from scanners, fax-to-email gateways, ERP/e-invoicing
  systems, and some mobile clients ("share as PDF"). The content is invisible to retrieval *and* leaves
  no attachment trace to OCR later. It is silent (no `failed`, no honest-NULL status) — the worst kind of
  loss.
- **Fix:** In `_extract_attachments`, handle the non-multipart case explicitly: if
  `not message.is_multipart()` and the top-level content type is not a body text type, emit ONE
  `ParsedAttachment` built from the whole message
  (`message.get_content_type()`, `message.get_payload(decode=True)`, `message.get_filename()`,
  `is_inline = message.get_content_disposition() == "inline"`). This routes the payload through the
  existing extraction seam (pdfplumber/openpyxl/etc.), so the Kaufland PDFs would extract normally.
  Guard against double-counting a single-part *text/plain* message (that one is correctly the body).
- **Found by:** content/attachment scout (empty-body + no-attachment cluster → raw MIME reproduction).

### 🟡 Medium

#### M1. Stored `headers` keys retain original wire-case — RFC 5322 case-insensitive names split into distinct JSONB keys

- **Root cause:** `headers.py:build_headers` (line 45) accumulates the header dict keyed by the header's
  **verbatim** name (`for key, value in message.items(): accumulated[key]...`), and `allowlist_headers`
  (line 101) filters on `key.lower()` but **preserves the original-case key** in the output. RFC 5322
  field names are case-insensitive, so two emails that spell the same header differently produce two
  different JSONB keys under the same logical header.
- **Evidence:** distinct lowercased key → casings across all 5,893 rows:
  - `message-id` → **`Message-Id` | `Message-ID`** (5,893 rows split across the two)
  - `cc` → **`Cc` | `CC`** (2,198)
  - `return-path` → **`Return-path` | `Return-Path`** (220)

  A consumer running `headers->>'Message-ID'` silently returns NULL for every `Message-Id` row; a GIN
  index or filter pinned to one casing misses the other. The allowlist itself is clean — all 22 distinct
  lowercased keys ⊆ the 24-key allowlist — so this is purely a key-normalization gap, not a leakage.
- **Impact:** Every Ask-layer / analytics consumer that reads a specific header must remember to
  lower-case or coalesce casings, or it under-reads. Affects every install (header casing varies by
  sender MTA). Latent correctness bug the schema doesn't advertise.
- **Fix:** Canonicalize header keys to lower-case in `build_headers` before the derivations run
  (`accumulated[key.lower()].append(...)`), or at minimum in `allowlist_headers`
  (`{key.lower(): value ...}`). One line; makes `headers->>'message-id'` total. Re-ingest/backfill to
  normalize existing rows.
- **Found by:** content scout (distinct-key enumeration with case grouping).

#### M2. Attachment text extraction mis-decodes cp1251/legacy-encoded Cyrillic into mojibake

- **Root cause:** the plain-text attachment path (`extractor_name='text-decode'`, for `.txt`/`.csv` with
  no MIME charset) and the TNEF interior text path (`extractor_name='tnefparse'`, `winmail.dat`) fall back
  to a Latin decode when no charset is declared, instead of detecting Windows-1251 (the dominant Bulgarian
  legacy encoding). The `decode_charset_chain` (M-5 strict fallback) has no declared charset to key on for
  a bare `.txt`/`.csv` and no statistical encoding detector, so cp1251 bytes render as Latin-1 mojibake.
- **Evidence:** 9 attachments carry double-decoded Cyrillic — e.g. `winmail.dat` → `Âàðí` (= `Варн…`,
  "Varna"), `Искания ШАБЛОН.csv` → `Âèä` (= `Вид`, "type"). By extractor: `text-decode` 6, `tnefparse` 3.
  Email **bodies are clean** (0 `Â`-mojibake; 14 honest `U+FFFD` fallbacks) — the gap is
  attachment-extraction-specific. NUL count is 0 (NUL stripping works).
- **Impact:** Small in count but disproportionately hits the DACH/BG target market — legacy-encoded
  Bulgarian/Cyrillic `.txt`/`.csv`/TNEF attachments become unsearchable garbage. Any install with
  non-UTF-8 legacy attachments is affected.
- **Fix:** Add statistical encoding detection (`charset-normalizer`, already a common dep) as the last
  resort in `decode_charset_chain` for undeclared-charset text and in the tnefparse interior decode —
  try declared charset → utf-8 → detector(cp1251/koi8/…) → strict Latin fallback. Verify against these 9
  rows before/after.
- **Found by:** attachment scout (mojibake regex over `extracted_text`, then per-extractor attribution).

### 🟢 Info / Observations

- **O1 — The blocklist has no storage-chokepoint backstop (defence-in-depth not landed).** The prior
  Critical's fix recommended two layers: a file/fetch-level skip **and** an `ingest_email(..., folder_role)`
  refusal at the storage chokepoint. Only the first landed — `ingest_imap_dump._drop_blocklist_folders`
  (line 177) and the fetch path filter files, but `email_ingest_service.ingest_email` (line 72) takes no
  folder argument and cannot refuse blocklist mail. Today's leakage is **0**, so this is not a live
  defect — but a future third caller (or a fetch-path regression) that reaches `ingest_email` without the
  file-level filter has no second line of defence. Consider threading `folder_role` into `ingest_email`
  and refusing an excluded role, so the invariant lives at the single chokepoint every driver shares.
- **O2 — Blocklist name heuristic is English-only; locale relies on optional RFC 6154 SPECIAL-USE.**
  `folder_policy._BLOCKLIST_SEGMENT_NAMES` = `{trash, deleted, deleted items, deleted messages, junk,
  spam, drafts}` — all English. Locale coverage depends entirely on the server advertising RFC 6154
  SPECIAL-USE flags (`\Trash`/`\Junk`/`\Drafts`), which is **optional**, and on **disk ingest there are
  no SPECIAL-USE flags at all** (`_drop_blocklist_folders` calls `is_excluded_folder(folder)` with no
  flags — verified line 188). For One AI's DACH target, a German mailbox on a server that doesn't
  advertise SPECIAL-USE would leak `Papierkorb` / `Entwürfe` / `Junk-E-Mail` through the name fallback.
  This corpus is unaffected (Courier server, English `INBOX.Trash`/`INBOX.spam`/`INBOX.Drafts`), so it is
  an observation, not a live finding — but it is a product-relevant gap: extend the word set with the
  locale terms for target markets (DE/BG/…), the same way `_GENERIC_DOMAINS` is extensible. (Also note
  singular `draft`/`bin` are deliberately excluded to avoid mail loss — accepted per the module docstring.)
- **O3 — Recipient addresses skip the addr-spec guard the FROM path has.** `email_parser._addr_spec_or_none`
  (line 233, audit L-7) coerces a non-addr-spec FROM token to NULL, but recipient addresses are stored
  verbatim. 7 recipient rows hold non-addr tokens: `undisclosed-recipients` ×3 (the RFC group-syntax
  `To: undisclosed-recipients:;`) and `mailto` ×4 (a `mailto:` token mis-split by `getaddresses`). The
  `address` column is `NOT NULL`, so a "who received X" consumer sees a recipient literally named
  `undisclosed-recipients`. Tiny (7 rows) but the same class as the guarded FROM path. Fix: apply an
  addr-spec filter to `recipient.address` (store NULL/skip when no `@`).
- **O4 — Vendor/tool domains minted as people-less companies; one distribution list minted as a person.**
  32 companies have no linked person (down from 77) — all are automated-sender domains observed via
  notification mail (`calendly.com`, `fathom.video`, `amadeus.net`, `europa.eu`), by design (DQ-C01: an
  automated sender's domain is still observed as a company, `from_person_id` NULL). `europa.eu` correctly
  folds 3 subdomains (`europa.eu`, `ec.europa.eu`, `nomail.ec.europa.eu`) under one company — eTLD+1
  folding still works. The **IDN quarantine also held**: `company_domain` has **0** `xn--` (punycode)
  domains and only the legit ASCII `breeze.no` is present — the `breeze.xn--n-1tb` homoglyph that fired
  the HITL quarantine twice during ingest did not leak into the graph. Separately, `ocenkiall@ocenki.bg`
  (a distribution list) is minted as a person
  because `is_role_address` doesn't catch the `…all` suffix — 1 row, cosmetic. Neither is a defect; both
  are noted for awareness.

      FROM email_recipient r WHERE r.email_id=m.id AND r.kind IN ('to','cc')) recipset,
   (SELECT string_agg(coalesce(a.content_hash,''),',' ORDER BY 1)
      FROM email_attachment a WHERE a.email_id=m.id) atthashes
  FROM email_message m JOIN d USING(message_id))
SELECT count(DISTINCT bodyhash) n_body, count(DISTINCT coalesce(recipset,'')) n_recip,
       count(DISTINCT coalesce(atthashes,'')) n_att
FROM rows GROUP BY message_id;   -- 8 groups → (1,1,1) html-split; 2 groups → (2,1,1) distinct emails
